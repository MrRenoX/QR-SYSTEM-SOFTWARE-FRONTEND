## Findings

### F-01 — Transitive high-severity vulnerabilities in Next.js's bundled `postcss`/`sharp`
**Severity:** HIGH
**File:** `package-lock.json` (`node_modules/next/node_modules/postcss`, `node_modules/sharp`)
**Current behavior:** `npm audit` reports 3 high-severity advisories (PostCSS source-map path traversal/XSS; sharp/libvips CVEs), all bundled *inside* Next.js 15.5.23's own dependency tree, not top-level dependencies of this project.
**Risk:** PostCSS's vulnerable path involves attacker-controlled `sourceMappingURL` comments processed at *build time* — this app only ever builds its own authored CSS/Tailwind output, never untrusted third-party CSS, so build-time exploitation requires an attacker who can already commit to the repo. `sharp` is used internally by `next/image` for optimizing local, developer-supplied images only (`public/images/**`) — no user-uploaded or remote images are processed anywhere in the app (confirmed: `images.remotePatterns: []`, zero remote `<Image>` sources in the codebase). Practical exploitability today is low.
**Recommended fix:** `npm audit fix --force` resolves it, but pulls in `next@16.3.0` — a **major version upgrade** of the framework running this entire app.
**Fix implemented:** Not applied. Per explicit instruction not to blindly upgrade major versions or risk breaking the approved UI, this is left as a tracked follow-up rather than an uncontrolled framework upgrade during a hardening pass. Recommend scheduling the Next 16 upgrade as its own dedicated task with full regression testing, separate from this audit.
**Verification status:** Confirmed via `npm audit` (see command log below). Re-run after any future dependency changes.

### F-02 — No ESLint installed or configured
**Severity:** LOW
**File:** `package.json`, (new) `eslint.config.mjs`
**Current behavior:** `eslint` was not a dependency at all; `npm run lint` (`next lint`) could not run without an interactive setup prompt, so lint had never been enforced.
**Risk:** No automated catch for common React/Next/TypeScript mistakes (missing hook deps, unsafe patterns, accessibility issues) before they ship.
**Recommended fix:** Install `eslint` + `eslint-config-next` (pinned to the installed Next major, v15) and a flat config extending `next/core-web-vitals` + `next/typescript`.
**Fix implemented:** Yes — added `eslint.config.mjs`, pinned `eslint-config-next@^15.5.23` (the initial unpinned install resolved to `eslint-config-next@16`, which threw a circular-JSON crash via `FlatCompat` — pinning to the matching major fixed it), changed `package.json`'s `lint` script from the deprecated `next lint` to `eslint .`. Fixed the one real finding it surfaced (missing `stops.length` dependency in `JourneyRoute.tsx`'s animation effect) and excluded the autogenerated `next-env.d.ts` from linting.
**Verification status:** `npm run lint` passes with zero errors/warnings (command log below).

### F-03 — Stray empty artifact directories in repo root
**Severity:** LOW
**File:** `{app/{experiences/[slug],book/[slug]},components,data,services,lib,public/images/{hero,experiences,touchpoints,illustrations,branding}}` (literal directory name)
**Current behavior:** A pre-existing, fully empty directory tree with literal `{`/`}` characters in its names — clearly the result of a `mkdir -p {app/{...},...}` brace-expansion command run in a shell that doesn't support brace expansion (e.g. Windows `cmd.exe`), creating the un-expanded string as a literal path instead of the intended folders.
**Risk:** No functional/security risk, but repo clutter that could confuse tooling or future contributors.
**Recommended fix:** Remove; confirmed zero files inside before deleting.
**Fix implemented:** Yes, removed.
**Verification status:** Directory listing confirms it's gone; `npm run build` unaffected.

### F-04 — `.env.example` would have been silently gitignored
**Severity:** LOW
**File:** `.gitignore`
**Current behavior:** The existing `.env*` ignore pattern also matches `.env.example`, which was about to be added as a required deliverable — it would never have been committed, defeating its purpose as a template for other developers.
**Risk:** Future developers/deployments would have no reference for required environment variables.
**Recommended fix:** Add a negation rule.
**Fix implemented:** Yes — added `!.env.example` after `.env*` in `.gitignore`.
**Verification status:** `.env.example` now created and not excluded; `.env`/`.env.local`/`.env.production.local` remain excluded.

### F-05 — No centralized API/service layer or request validation existed
**Severity:** INFO (architecture readiness, not a vulnerability in the current frontend-only state)
**File:** `components/ContactForm.tsx`, `QueryForm.tsx`, `BookingForm.tsx` (previously), now `services/*`, `lib/validation/*`
**Current behavior (before):** Forms called `setSent(true)`/`setConfirmed(true)` directly with no validation beyond native HTML `required`/`type` attributes, no length limits, and no path prepared for a real backend call.
**Risk:** Without server validation existing yet, HTML-only validation is trivially bypassed (devtools, disabled JS); no consistent error/loading UX; every future backend hookup would require rewriting form logic.
**Recommended fix:** Centralized `lib/validation/*` (name/email/phone/length limits per the spec), a typed `services/apiClient.ts` → `contactService`/`queryService`/`bookingService` layer, with forms calling services instead of managing state ad hoc.
**Fix implemented:** Yes, in full — see `API_INTEGRATION.md` for the architecture. Forms now validate before submission (never trust HTML validation alone), enforce max lengths via `maxLength` **and** JS validation, show field-level errors, disable the submit button + show "Sending…" during submission (double-submit guarded), and branch on a typed `ApiResult` for success/error UI.
**Verification status:** Manually tested in a real browser: invalid input (short name, malformed contact, short message) is blocked with visible field errors and does *not* reach the success state; valid input reaches the success state via the mock-mode fallback (no backend configured yet).

### F-06 — No Cloudflare Turnstile / human-verification gate existed
**Severity:** INFO (feature gap, not a vulnerability)
**File:** (new) `components/security/HumanVerification.tsx`, `components/security/VerificationGate.tsx`
**Current behavior (before):** No bot-check of any kind before content was shown.
**Risk:** A public QR-triggered site with no verification is easy to script against (scraping, spam form submission at volume) once a backend exists.
**Recommended fix:** Real Cloudflare Turnstile widget (not a fake checkbox), gating content once per browser session.
**Fix implemented:** Yes. `HumanVerification.tsx` loads the real Turnstile script and renders the actual widget via `window.turnstile.render(...)`, handling loading/success/error/expired states with a retry action. `VerificationGate.tsx` wraps `MobileShell`'s children, remembers verification for the current `sessionStorage` session only, and **automatically bypasses the entire gate when `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is unset** — so local dev, this build, and this audit's own tests keep working with zero configuration, and the gate activates automatically the moment a real site key is provided. No fake/pretend verification exists — with no key, there is visibly no gate, not a checkbox pretending to check anything.
**Verification status:** Confirmed via production build + headless browser: with no site key set, every route renders full content immediately, no gate shown, no console errors. Server-side Turnstile `siteverify` is explicitly **not implemented** (frontend-only scope) — see `API_INTEGRATION.md` for what the future Flask API must do with the token.

### F-07 — No security headers or CSP were configured
**Severity:** INFO (hardening gap)
**File:** `next.config.ts`
**Fix implemented:** Added `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` (camera/mic/geolocation/payment/usb all denied — none are used), `Strict-Transport-Security`, and a `Content-Security-Policy` scoped to only what's actually used (`self`, Cloudflare Turnstile for script/connect/frame, `data:` for images/fonts, plus the future API origin read from `NEXT_PUBLIC_API_URL` at build time). See `next.config.ts` inline comments for why `'unsafe-inline'` is kept on `script-src`/`style-src` (Next's RSC inline bootstrap scripts, and this UI's extensive use of inline `style={{...}}` for scroll-reveal/journey-route animations — removing it would either break the build or break approved, existing animations). A stricter nonce-based CSP via middleware is a valid follow-up but wasn't attempted here to avoid an under-tested change to every page's hydration.
**Verification status:** Confirmed via `curl -I` against a production build — all headers present with expected values (log in `FRONTEND_PRODUCTION_CHECKLIST.md`). Confirmed via headless browser across all 10 routes: zero CSP violation errors in console.

### F-08 — No `app/error.tsx` or `app/loading.tsx`
**Severity:** INFO
**Fix implemented:** Added both. `error.tsx` shows a generic, friendly message and a retry button — it deliberately does **not** log the error to the console (a placeholder comment marks where a real error-tracking service integration belongs later) and never renders `error.message`/stack traces to the guest. `loading.tsx` is a minimal branded spinner.
**Verification status:** `npm run build` includes both in the route manifest; `app/not-found.tsx` (already existed) was left untouched.

### F-09 — Console logging audit
**Severity:** INFO
**Finding:** Zero `console.log`/`console.error`/`console.warn`/`debugger` statements exist anywhere in `app/`, `components/`, `lib/`, `services/`, or `data/`. Nothing to remove.
**Verification status:** Repo-wide grep, confirmed clean.

### F-10 — XSS / unsafe-HTML audit
**Severity:** INFO
**Finding:** Zero uses of `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `new Function`, or `document.write` anywhere in first-party source. All user-facing text is rendered through normal JSX text interpolation (`{value}`), which React escapes by default.
**Verification status:** Repo-wide grep, confirmed clean. No sanitization library was needed since no rich-HTML rendering exists or is planned.

### F-11 — Storage audit
**Severity:** INFO
**Finding:** No `localStorage` use anywhere. `sessionStorage` is used in exactly one place — `VerificationGate.tsx` — storing a single boolean-like flag (`"1"`) under key `gg_verified`, nothing else. No PII, tokens, or secrets are stored client-side anywhere in the app.
**Verification status:** Repo-wide grep, confirmed.

## What was explicitly verified as already safe (no fix needed)

- **URL/redirect security:** the only `searchParams` usage (`app/experiences/page.tsx`'s `?category=`) is validated against the real category list returned by `getCategories()` — an unrecognized value simply falls back to "All"; it is never used to construct a redirect or arbitrary navigation. No `redirect()`, no `window.location` assignment, no open-redirect surface exists anywhere in the app.
- **Dynamic route slugs:** `/experiences/[slug]` and `/book/[slug]` both look up the slug against real data and call Next's `notFound()` when it doesn't match — confirmed this renders the branded 404 page correctly for both routes, including malformed slugs.
- **External links:** every existing `target="_blank"` already had `rel="noopener noreferrer"` before this audit began.
- **Images:** every `next/image` source is a local `/images/**` path; `images.remotePatterns` is explicitly set to `[]` to document that no external image host is trusted.
- **Secrets:** no API keys, passwords, tokens, or credentials of any kind exist anywhere in the repository (verified by pattern search across all `.ts`/`.tsx` source).

# Backend Build Guide — Anubhav / Guide Guru Global

This is the complete reference for building the Flask + MySQL backend for this
project. It consolidates every schema and API decision made while designing
against the existing Next.js frontend (public QR site + Super Admin panel).

The frontend is already built and expects exactly the shapes documented here.
Nothing in `app/`, `components/`, `services/`, or `types/` needs to change if
you follow this guide — you're filling in the other end of contracts that
already exist in the frontend code.

---

## 1. Architecture

```
Next.js Frontend (public site + /dashboard/super-admin)
        │
        │  fetch, via services/apiClient.ts + services/admin/*
        ▼
Flask REST API   (NEXT_PUBLIC_API_URL)
        │
        ▼
   MySQL Database
```

- Public site: `services/apiClient.ts`, `services/experienceService.ts`,
  `contactService.ts`, `queryService.ts`, `bookingService.ts`
- Admin panel: `services/admin/*.ts` (same `apiClient.ts`, adds an
  `Authorization: Bearer <token>` header)
- Until `NEXT_PUBLIC_API_URL` is set, every service resolves with mock data —
  going live is exactly: build the endpoints below, set the env var, done.

## 3. API Endpoints

All admin endpoints require `Authorization: Bearer <token>` and should
`403` (not just hide in the UI) for roles that shouldn't access them — the
frontend's route guard is client-side convenience only, not real security.

Every route lives under the `/api/v1/` prefix (matches what's already
built for Experience/Category — see 3.3/3.4 for the full request/response
detail on Query and Booking). Status column: **✅ Live** = built and
verified against the running backend; **⏳ Planned** = frontend already
calls it in "live mode" once `NEXT_PUBLIC_API_URL` is set, but the route
doesn't exist yet; **❌ Not started** = frontend is still 100% local mock,
doesn't even attempt a real call.

### 3.1 Public

| Status | Method | Path | Notes |
|---|---|---|---|
| ✅ | GET | `/api/v1/experience` | list, only `status='active'` |
| ✅ | GET | `/api/v1/experience/:id` | full detail incl. `stops`, `pricing_options`, `slots` |
| ✅ | GET | `/api/v1/category` | active categories only |
| ✅ | POST | `/api/v1/query` | see 3.3 below — full detail |
| ✅ | POST | `/api/v1/booking` | see 3.4 below — full detail |
| ✅ | POST | `/api/v1/contact` | see 3.5 below — full detail |
| ⏳ | GET | `/api/v1/settings` | **new — not built yet.** Read-only, public, no auth. Returns the exact same `general`/`social`/`homepage`/`footer` blobs as `GET /api/v1/admin/settings` (see 2.8) — frontend only reads `websiteName/phone/email/whatsapp/address` from `general`, `instagram/facebook/youtube` from `social`, `heroTitle/heroSubtitle` from `homepage`, and `description/copyright` from `footer`. Powers the public site's header/footer contact info and homepage hero copy, which today are hardcoded — see `services/settingsService.ts`. ⚠️ **Security:** GET only, no write access, no auth required (this data is already meant to be publicly visible) — but for exactly that reason, never add secrets/internal fields (API keys, tokens, `qr_website`'s config, etc.) into the `general`/`social`/`homepage`/`footer`/`contact` blobs, since anything in them becomes world-readable the moment this route exists. | ⏳ | GET | `/api/v1/faq` | **new — not built yet.** See 3.6 below — full detail. Read-only, public, no auth, only `status='active'`. Powers the public FAQs page, which today renders a hardcoded list — see `services/faqService.ts`. |

### 3.3 Query API (detailed)

Guest "raise a query" form — a question about an experience (or a general
one), no payment/booking involved. Shown on the experience detail page
under "Raise a query". JSON body (`Content-Type: application/json`).

#### 1. Submit Query (Public — guest form)

**`POST /api/v1/query`**

| Field | Type | Required | Notes |
|---|---|---|---|
| `guest_name` (ya `name`) | text | ✅ | dono key names accept karo — public form `name` bhejta hai |
| `room_number` | text | ❌ | |
| `mobile` | text | ✅ | |
| `experience_id` | number | ❌ | agar diya to existing experience ka `id` hona chahiye (warna `404`), na diya to query kisi experience se tied nahi hoti (`experience_id = NULL`) |
| `question` | text | ✅ | |
| `turnstile_token` | text | ❌ | Cloudflare Turnstile token — server-side verify karna ho to `siteverify` call karo (see section 4) |

`status` guest nahi bhejta — default `"New"` hota hai, admin PATCH se change karta hai.

**Response `201`**
```json
{
  "success": true,
  "message": "Query submitted successfully",
  "data": {
    "id": 1,
    "guest_name": "Sita Devi",
    "room_number": "101",
    "mobile": "9998887766",
    "experience": { "id": 10, "title": "Ayodhya Spiritual Journey" },
    "question": "Kya darshan slot badal sakte hain?",
    "status": "New",
    "created_at": "2026-08-17T11:53:44",
    "updated_at": "2026-08-17T11:53:44"
  }
}
```

`experience` null hota hai agar `experience_id` bheja hi nahi tha.

**Errors**
- `400` — body JSON nahi hai
- `422` — validation failed
- `404` — `experience_id` diya lekin exist nahi karta

```js
const res = await fetch(`${BASE_URL}/api/v1/query`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    name: "Guest Name",           // ya "guest_name"
    room_number: "204",
    mobile: "+91XXXXXXXXXX",
    question: "Kya bacchon ke liye bhi ye experience theek hai?",
    experience_id: 10,            // optional
  }),
});
const json = await res.json();
```

| Field | Type |
|---|---|
| `status` | `New` \| `In Progress` \| `Resolved` \| `Closed` |

#### 5. Delete Query (Admin)

**`DELETE /api/v1/admin/query/:id`** — `404` if not found.

### 3.5 Contact API (detailed)

Public Contact Us form message. JSON body (`Content-Type: application/json`).

#### 1. Submit Contact Message (Public — Contact Us form)

**`POST /api/v1/contact`**

Current frontend (`ContactForm.tsx`) only collects a single combined
`contact` field (phone *or* email, not both) — the backend handles that
without any frontend change needed:

| Field | Type | Required | Notes |
|---|---|---|---|
| `name` | text | ✅ | |
| `email` | text | ❌* | valid email format |
| `mobile` | text | ❌* | |
| `contact` | text | ❌* | **fallback field** — used when `email`/`mobile` aren't given separately: `"@"` present → treated as `email`, else → `mobile`. Not stored itself, just parsed |
| `subject` | text | ❌ | defaults to `"General Inquiry"` if not given |
| `message` | text | ✅ | |
| `turnstile_token` | text | ❌ | |

\* `email`, `mobile`, `contact` are each individually optional, but **at
least one** of `email`/`mobile` (given directly or resolved from `contact`)
is required, or `422`.

**Response `201`**
```json
{
  "success": true,
  "message": "Message submitted successfully",
  "data": {
    "id": 1,
    "name": "Ravi Sharma",
    "email": "ravi@example.com",
    "mobile": null,
    "subject": "General Inquiry",
    "message": "Group booking discount hai kya?",
    "status": "Unread",
    "created_at": "2026-08-17T11:53:45",
    "updated_at": "2026-08-17T11:53:45"
  }
}
```

**Errors**
- `400` — body JSON nahi hai
- `422` — `email`/`mobile`/`contact` teeno missing, ya koi field validation fail

```js
const res = await fetch(`${BASE_URL}/api/v1/contact`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    name: "Ravi Sharma",
    contact: "ravi@example.com",   // ya phone number, backend khud pehchan leta hai
    message: "Group booking discount hai kya?",

});
```

#### 4. Update Contact (Admin)

**`PATCH /api/v1/admin/contact/:id`** — send only the fields changing.
Admin sets `status` from here (and can correct `name`, `email`, `mobile`,

| Field | Type |

| `status` | `Unread` \| `Read` \| `Replied` \| `Closed` |

#### 5. Delete Contact (Admin)

### 3.4 Booking API (detailed)

Guest booking request from the "Book this experience" flow. Doesn't take
payment — just creates a `Pending` booking that reception confirms and
follows up on over WhatsApp. Booking endpoints take a **JSON body**
(`Content-Type: application/json`), not multipart — no file upload here.

#### 1. Create Booking (Public — guest form)

**`POST /api/v1/booking`**

| Field | Type | Required | Notes |
|---|---|---|---|
| `experience_id` | number | ✅ | existing experience ka `id` — resolve to `bookings.experience_id`. Na mile to `404 Experience not found` |
| `guest_name` | text | ✅ | 1–100 chars |
| `room_number` | text | ❌ | |
| `mobile` | text | ✅ | frontend `whatsapp` bhi bhej sakta hai — dono keys accept karo, same field |
| `email` | text | ❌ | valid email format, warna `422` |
| `visit_date` (ya `date`) | text (`YYYY-MM-DD`) | ✅ | dono key names accept karo (`date` reserved word hai isliye DB column `visit_date` hai) |

## 4. Auth

- Password hashing: bcrypt or argon2, never plaintext, never MD5/SHA1.
- Token: JWT is fine — put `sub` (admin id), `role`, `exp`. Frontend stores it
  as an opaque string in `localStorage`/`sessionStorage` (see
  `services/admin/authService.ts`) and sends it back as `Authorization:
  Bearer <token>`.
- RBAC: enforce the 4 roles (`super_admin`, `content_manager`,
  `booking_manager`, `support`) **server-side** per endpoint. The admin
  sidebar/pages don't currently hide anything per-role — that's frontend
  work to add later if needed, but don't rely on it for security either way.
- Cloudflare Turnstile: the public site's `HumanVerification` component
  (`components/security/HumanVerification.tsx`) obtains a token client-side.
  If you want to verify it server-side (recommended for the contact/query/
  booking endpoints), call Cloudflare's `siteverify`:
  ```
  POST https://challenges.cloudflare.com/turnstile/v0/siteverify
  { "secret": TURNSTILE_SECRET_KEY, "response": <token> }
  ```
  `TURNSTILE_SECRET_KEY` is backend-only — never put it in the Next.js repo
  or any `NEXT_PUBLIC_*` variable.
